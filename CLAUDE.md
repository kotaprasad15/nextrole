# NextRole — CLAUDE.md

Multi-agent job search + outreach platform. Prompting, tool use and orchestration only (no fine-tuning).
Full design: see the approved proposal (agents, schemas, data model, milestones a–g).

## Commands
- Install: `uv sync`
- Tests: `uv run pytest -q` (LLM and HTTP always mocked)
- Lint: `uv run ruff check .`
- Live baseline demo: `uv run python -m nextrole.baseline_demo` (needs `.env` with `ANTHROPIC_API_KEY`)

- Evaluation (spends real tokens; see `eval/README.md`): `uv run python -m eval.run_eval {tiering|outreach|p10-sheet|p10-score|report}`
- Security: `uv run python -m nextrole.security genkey|rotate|encrypt-existing` (key management), `bash scripts/audit.sh` (pip-audit, npm audit, gitleaks, secret scan; needs network), `uv run pytest -q tests/security` (adversarial suite). Details and threat model: `docs/SECURITY.md`.
- Alerts once by hand (cron-friendly): `uv run python -m nextrole.alerts_job`.
- Live job discovery (no key needed): `uv run python -m nextrole.jobs_demo "software engineer" "remote"`

- App: two processes. API: `uv run uvicorn nextrole.api.main:app --reload` (port 8000; set `RESUME_ENCRYPTION_KEY` in `.env` first). UI: `cd frontend && npm install && npm run dev -- -p 3100`, open http://127.0.0.1:3100 (the Next app proxies `/api/*` to the API, `BACKEND_URL` in `frontend/.env.local`, default `http://127.0.0.1:8000`; leave `NEXT_PUBLIC_API_MODE` unset for the real API). Production UI: `npm run build && npm start`.

## Frontend (`frontend/`, the only UI)
Next.js 16 (App Router, React 19, TypeScript strict) + Tailwind v4 + Radix, "Paper & Ink" light theme. The old framework-free UI that FastAPI used to serve (`src/nextrole/web/`) has been REMOVED: FastAPI now serves only the API, and `GET /` returns a small JSON pointer to `/docs` and this app.
- Commands (run in `frontend/`): `npm run dev` (use `-p 3100`), `npm test` (Vitest), `npm run typecheck`, `npm run lint`, `npm run build`. Design system lives at `/design` (living style guide).
- **Read `frontend/node_modules/next/dist/docs/` before using a Next API**: this Next version has breaking changes (e.g. `middleware.ts` is now `proxy.ts`; `cacheComponents` is on, so keep data fetching client-side or in Suspense).
- **Themes**: light = `@theme` in `globals.css`; dark = the `:root.dark` block right after it (same token names, so utilities re-theme with no component changes; keep that block flat because `tokens.contrast.test.ts` parses it, and keep it `:root.dark` not `.dark`: a later `:root {}` block would otherwise win). `next-themes` (in `Providers`, `attribute=class`, default system, key `theme` in localStorage) sets the class before first paint. `ThemeToggle` (marketing nav, app nav, auth pages) renders both icons and lets CSS (`dark:` variant = `.dark` class) pick, so there is no hydration mismatch; Settings has System/Light/Dark. Tier FILL colours are identical in both themes; only the `-ink` text shades and `-tint` backgrounds flip. Text on fills uses `text-on-primary|on-startup|on-mid|on-danger|on-ink`, never `text-white` on a token that changes. Contrast tests run for BOTH themes (including the glass and hero backdrop, which is dimmed in dark by `DARK_WASH`).
- **Tokens are the single source of truth**: CSS variables in `frontend/src/app/globals.css` (`@theme`). Never hard-code hex values in components. `src/lib/tokens.contrast.test.ts` parses that file and enforces WCAG AA. Coral/teal/warning/success are too light for text on white: use fills/rings/glows with the brand colour and the matching `-ink` shade for text; text on coral/teal fills is `ink`, not white.
- Tier colours/labels come from `src/lib/tier.ts` only (`TIER_META`); use `TierBadge`, never re-style tiers ad hoc.
- Components in `src/components/ui/` follow shadcn conventions (Radix primitives, `cva`, `cn`) but are hand-written and restyled; no shadcn CLI. Motion tokens/hooks are in `src/lib/motion/` (`tokens.ts`, `hooks.ts`, `magnetic.tsx`); never put animation numbers or pointer logic inline in pages. Animate transform/opacity only.
- Hydration rule: anything that reads browser state (reduced motion, pointer type) must come from the hooks in `lib/motion/hooks.ts` (matchMedia via `useSyncExternalStore` with a fixed server snapshot). Do not call framer's `useReducedMotion` directly (its server and first-client values differ and caused a hydration mismatch). Components that animate in (e.g. `ScoreRing`) must render the same initial state on server and client.
- Rich effects (tilt, magnetic) only when `useRichMotion()` is true (fine pointer and motion allowed); touch gets tap feedback. There is NO custom cursor any more (removed): the system cursor is always used.
- UI work needs no backend and no LLM calls: development, tests and screenshots use **mock mode** (set `NEXT_PUBLIC_API_MODE=mock` in `frontend/.env.local`; if the real app suddenly shows sample data like "Priya Nair", that line is still set); draft version history is client-side (localStorage); saved jobs, watched companies and roles are SERVER-side (mock mode keeps them in localStorage keys `nextrole_mock_saved` / `nextrole_mock_companies`); ATS Check is in-browser.
- **API layer** (`frontend/src/lib/api/`): `schemas.ts` (Zod = the one definition of every response; types are `z.infer`), `client.ts` (`apiRequest`: JSON/FormData, `ApiError`, validates responses, calls the 401 handler), `endpoints.ts` (`api.*`, one function per route), `routes.ts` (route table), `queries.ts` (TanStack keys/hooks), `sse.ts` (`useRunEvents`, de-dupes by `seq`). Pages call `api.*` via TanStack Query; never `fetch` directly. `npm run check:api` (needs the backend running) verifies every route exists in its OpenAPI; `LIVE_BASE=... LIVE_COOKIE=... npm test -- contract.live` parses the real backend's JSON with the schemas (read-only, no LLM).
- **Mock mode** (`NEXT_PUBLIC_API_MODE=mock`, set in `.env.local`, gitignored): `lib/api/mock/` is an in-memory fake backend (same routes, status codes, shapes; fixtures use fictional companies; simulated runs stream the real event shapes). Dev switches in `localStorage.nextrole_mock` (JSON): `delay`, `empty`, `fail:["recommendations"]`, `speed`, `expired`. Fixtures are held to the same Zod schemas by tests. Demo login: any email + 8+ char password (`wrong-password` simulates a 401; `taken@example.com` a 409).
- **Auth/routing**: `src/proxy.ts` (Next 16's `middleware`) only checks that the `nextrole_session` cookie EXISTS (rules in `lib/route-guard.ts`, unit-tested, `safeNext` blocks open redirects); real validity comes from `GET /me`. `AppShell` registers the 401 handler: it calls backend `POST /auth/logout` FIRST (the cookie is HttpOnly, only the server can clear it; otherwise the guard bounces /login back to the page that 401s: a redirect loop), then redirects to `/login?next=`. The handler lives in `components/shell/use-session-guard.ts`, shared by `AppShell` and `FlowShell` (focused signed-in flows in the `(flow)` route group, e.g. `/onboarding`, no app nav).
- **Auth + onboarding (M3)**: forms validate with Zod rules in `lib/validation.ts` (mirror the backend: email regex; NEW passwords need 8-256 chars with an uppercase, a lowercase and a special character, shown as a live `PasswordChecklist`, plus a confirm field; the server enforces the same in `auth/policy.py` and login accepts any existing password; the server stays the authority) and server errors are mapped onto fields by `lib/auth-errors.ts` (401 stays form-level and never says which half was wrong: no account enumeration). After login `GET /profile` 404 sends the user to `/onboarding`. The wizard (`components/onboarding/`, rules in `lib/onboarding.ts`) holds steps 1-2 in memory and sends everything with the resume in ONE multipart `POST /onboarding` (the backend parses in that call), then review edits the profile via `PUT /profile`. Step changes move focus to the step heading. Primitives: `TagInput`, `Switch`, `RadioCards`, `FileDropzone`, `PasswordInput` (they take `ref`/`id`/`aria-*` as plain props: React 19, so `Input` etc. use `ComponentProps<"input">`). Mock `speed` also scales the resume-parse delay.
- **Dashboard (M4)**: `components/dashboard/dashboard.tsx` composes tier tabs (counts reflect filters), `FiltersBar`, `JobCard`, `RunPanel` (live SSE feed folded by `lib/dashboard/run-steps.ts`: one row per planned step, extra rows for rewrite attempts) and `PasteJobModal` (rules in `lib/dashboard/paste.ts` mirror the backend: https only, no LinkedIn/Indeed/Naukri fetch, text wins). Filtering/sorting is pure client code in `lib/dashboard/filters.ts`. Saved jobs come from the server through `lib/saved/use-saved-jobs.ts` (`useSavedJobs()`: `ids`, `isSaved`, `toggle`, `setStatus`, built on TanStack Query key `keys.saved`). One run at a time: a 409 shows a toast and a run still `running` on the server is re-attached on load. When a run ends, recommendations/outreach/runs queries are invalidated once. - **Job detail + outreach (M5)**: dynamic pages are server components that `await params` inside `<Suspense>` and hand a plain id to a client component (`jobs/[id]/page.tsx`). `JobDetail` is built from the scored match plus, if a draft exists, its `facts_used` (the API has no job-description or single-job endpoint; without a draft it says so). `OutreachPage` = `GenerateForm` (no draft: `POST /runs` outreach via `useOutreachRun`, live `RunPanel`) or `DraftEditor` (edit/save/copy/approve/regenerate/delete; reviewer panel; facts with https-only source links; feedback). Approval is the only path to the mailto/Gmail links, built client-side from the typed address (`lib/outreach.ts`); approving an unreviewed or edited draft asks for confirmation; unsaved edits trigger `beforeunload`. Editing clears review+approval server-side and the UI says so. Draft **version history is local** (`lib/local/draft-versions.ts`, versioned, capped at 20 per job; a snapshot is recorded when the loaded draft differs from the newest one: "generated" if reviewed, else "edited"; compare uses `lib/diff.ts` line diff with +/- markers; restore only fills the editor). `/outreach` list joins `GET /outreach` rows with current matches (job may have left the matches). Query keys: `outreachByJob` shares the `["outreach"]` prefix, so invalidating `keys.outreach` also refetches drafts.
- **ATS Check (M6)**: deterministic and fully in-browser, no network and no LLM (a test asserts `fetch` is never called). Engine in `lib/ats/`: `dictionary.ts` (aliases, skills, stop words), `keywords.ts` (`normalize`/`tokens` with identical canonicalisation + light stemming on both sides; `extractKeywords` = known skills + words the posting repeats, marked required/preferred/general from headings ("Requirements:", "Nice to have:") and cue words; bulleted lines are never headings), `checks.ts` (sections + formatting issues, each with a concrete fix), `analyze.ts` (score = 60% keyword coverage weighted 3/2/1 + 20% sections + 20% formatting; `projectedScore` = estimate if missing required/preferred keywords were truthfully added). It is labelled a heuristic estimate, not any real ATS. `extract-text.ts` parses PDF (`pdfjs-dist`, worker via `new URL(..., import.meta.url)`) and DOCX (`mammoth/mammoth.browser.js`, typed in `src/types/mammoth.d.ts`) with LAZY dynamic imports so they only load on `/ats`; extracted text lands in an editable box so users see what a parser reads. Verified with a real PDF and DOCX in the browser. Suggestions always say to add only skills the user really has.
- **Profile and Saved jobs (M7, reworked)**: `/profile` = `ProfilePage` with tabs Profile / Preferences (READ-ONLY by default: a disabled `<fieldset data-readonly>` makes every control inert, `data-edit-only` controls are hidden by CSS; "Edit profile" switches to edit mode with Save / Cancel, Cancel asks first when there are unsaved changes; one shared draft, saved with `PUT /profile`, which only ever touches the caller's own row (the user comes from the session, never the body); rules in `lib/profile-form.ts`; sticky save bar + `beforeunload` when dirty). The Preferences tab also shows `RoleReading` (how the server's role taxonomy reads each wanted role) and `WatchedCompanies` (saved immediately through `/companies`, independent of edit mode; companies we cannot read a board for carry a "not watchable yet" badge). `/saved` = `SavedPage`: server-side filters (status, company type, listing, search, sort), per-job status select (Saved/Applied/Interview/Offer/Rejected), notes saved on blur, a "No longer listed" badge and no Apply link for postings the employer removed, two-step remove, and a one-time banner that moves anything an older version kept in this browser (`nextrole_saved_jobs`, `nextrole_tracker`, read by `lib/local/legacy-saves.ts`) to the account via `POST /saved-jobs/import`. The old browser-only tracker/board was removed.

Leaving a media query or unmounting reverts all tweens/triggers and destroys Lenis. Motion contract: timelines only touch `[data-el="..."]` elements the static scenes render and END in the static markup's state (tests render each scene and run its builder against a recording timeline); numbers shared via `lib/marketing/constants.ts`. The hero headline reveal is CSS-only (`word-rise` with per-word delay) so nothing flashes before JS. Sample visuals are labelled "for illustration"; copy only claims what the product does (no sending, real job boards, no LinkedIn scraping). In the browser tool the screenshot is an unscaled top-left 800x500 crop of a 1280 viewport, so desktop scene state was verified through computed styles at scroll positions.

Scrollbar hidden site-wide: homepage has `ScrollRing` (rotating conic progress + section name, `lib/marketing/active-section.ts`), app pages a CSS scroll-driven `.app-progress` line. If you add a new `--text-*`, `--radius-*` or `--shadow-*` token, add it to that config, or tailwind-merge will silently DROP classes (this once removed white text from primary buttons). `cn.test.tsx` guards it.

Only one `next dev` per project folder. jsdom lacks `matchMedia`/`IntersectionObserver` (stubbed in `vitest.setup.ts`).

## Architecture (current: milestone g)
- `config.py`: all tunables from `.env` (model names, budgets, prices). Never hardcode a model.
- `llm/client.py`: the only gateway to Anthropic. Retries (transient only), timeout, budget check, tracing, JSON output validated by Pydantic with one repair retry.
- Provider: `LLM_BASE_URL` (empty = Anthropic) points the same SDK at any Anthropic-compatible endpoint, e.g. DeepSeek `https://api.deepseek.com/anthropic` with `MODEL_FAST=deepseek-flash`, `MODEL_STRONG=deepseek-v4-pro`. Set `PRICE_*` to that provider's rates. PII caveat: DeepSeek hosted API is for sample resumes only.
- `llm/budget.py`: per-run token/cost cap (`BudgetExceeded`).
- `tracing/`: JSONL trace per run in `traces/`, always passed through `redact()` (sensitive keys dropped, emails/phones/tokens masked, long text = length+hash only, no prefix).
- `models/`: Pydantic types. `HttpsUrl` enforces https; `Job.apply_url` is set only by source connectors.
- `sources/`: `BoardSource` connectors (Greenhouse, Lever, Ashby) normalize public ATS payloads into `Job`; `registry.discover()` fans out in parallel with timeouts/retries, records per-board errors instead of failing, filters by `Preferences`, and dedupes. Boards are curated in `data/boards.json`. Apply URLs are copied verbatim from the API; non-https rows are skipped.
- `db/`: sqlite3 + `schema.sql` + `repos.py` functions (no ORM). Cascade deletes: deleting a user removes sessions/profile; the encrypted resume file is deleted by the caller (`DELETE /me`). One shared connection (`check_same_thread=False`) is fine for the demo; use per-request connections before real deployment.
- `auth/`: Argon2id password hashes; `policy.py` = signup password rules (8-256, upper, lower, special; login accepts older passwords); opaque server-side sessions (only SHA-256 of the token stored; HttpOnly SameSite=Lax cookie, Secure in production). Login is throttled per IP and per email and locks an account for 15 min after 5 failures (`users.failed_logins/locked_until`).
- `resume/`: `inspect.py` (magic bytes, size/page limits, rejects scripts/macros/zip bombs/encrypted files, removes hidden text, flags injection phrases, returns a SANITIZED copy), `worker.py` + `sandbox.py` (the parse runs in a child process with a timeout; `RESUME_ISOLATION=false` only for tests), `extract.py` (in-process helper), `storage.py` (`ResumeStore`: AES-256-GCM files; reads old Fernet files). The onboarding route stores the sanitized copy, never the raw upload.
- `agents/intake.py`: resume text -> `Profile` via `ExtractedProfile` schema; resume is untrusted data (injection guard in prompt, schema-constrained output).
- `api/`: `create_app(settings, conn, llm_factory)` factory (injectable for tests). Routes: `/auth/signup|login|logout`, `DELETE /me`, `POST /onboarding` (multipart), `GET /me`, `GET|PUT /profile`. Run: `uv run uvicorn nextrole.api.main:app --reload`.
- `agents/tiering.py`: startup/mid/mnc. Order: DB cache -> `data/mnc_seed.json` -> employee-count thresholds (`tier_from_employee_count`, no source supplies counts yet) -> one batched LLM call. Every confident (>=0.6) decision is cached in `company_tiers`; low-confidence ones are not.
- `agents/matcher.py`: `select_candidates` (rank within each tier by keyword overlap + seniority fit, per-company cap, round-robin across tiers so every dashboard section gets candidates) then `MatcherAgent` scores each with the LLM (0-100, strengths, gaps, 1-sentence rationale; concurrent, one failure drops one job, budget exhaustion stops cleanly). Prompt contains no URLs.
- `recommend.py`: pipeline discover -> tier all companies -> select -> match -> persist (`jobs`, `matches` tables). Milestone f wraps it in LangGraph. API: `POST /recommendations/refresh`, `GET /recommendations` (grouped by tier; `apply_url` read from stored source data). Prices in `.env` (`PRICE_*`) must match the provider or reported cost is wrong.
- Reasoning models (e.g. DeepSeek) can spend `max_tokens` before emitting text; keep generous headroom (matcher 1000, tiering 400+80/company) because a truncated JSON reply costs a retry.
- `tools/`: `netguard.check_public_https` (SSRF guard: https only, no creds/odd ports, all resolved IPs public, redirects re-checked), `cache.HttpCache` (SQLite TTL) + `HostRateLimiter`, `research_tools.ResearchTools` (`company_overview` = Wikipedia API, `company_news` = Hacker News Algolia API filtered by title/points, `fetch_page` = guarded, only on hosts already seen). Every result is a numbered source (R1..) with the URL from the API; the model cites ids and never writes URLs. Google News RSS was rejected (terms restrict it to personal feed readers).
- `agents/researcher.py`: bounded tool-use loop (`research_max_steps`), then a separate schema-validated extraction call. Facts/news are rebuilt from our own source records; facts citing unknown sources or containing URLs are dropped. Research is cached per company (`research_cache`, 24h; empty results not cached).
- `agents/factsheet.py`: the closed set of facts (F-P profile, F-J job, F-R research) the Writer may use. No contact details.
- `agents/writer.py` / `agents/critic.py`: Writer cites fact ids per claim; Critic = deterministic rules (no URLs/placeholders, real fact ids, subject present, word range) + LLM rubric (specificity, tone, grounding, no_fluff) + `unsupported_claims`. Pass needs overall >= `critic_threshold`, no unsupported claims, no violations.
- `outreach.py`: research -> fact sheet -> write<->critic loop, max `critic_max_retries` rewrites (so up to 4 drafts); keeps the BEST draft (pass > fewer problems > higher score), warns if never passed, degrades to job-only facts if research fails, returns best-so-far on budget exhaustion.
- Outreach API (`api/routers/outreach.py`): `POST /outreach` (job must be in the user's matches), `GET /outreach`, `GET /outreach/by-job/{id}`, `PUT /outreach/{id}` (edit: resets status to draft, clears critic, drops approval), `POST /outreach/{id}/approve` (the ONLY path to `user_approved`), `DELETE`. There is deliberately no send endpoint (a test asserts this). One record per (user, job); regenerate replaces it but keeps the recipient email.
- `LLM_DISABLE_THINKING=true` (needed for DeepSeek): reasoning models otherwise burn `max_tokens` on hidden thinking and return empty text. Pasted job URL/text flow is deferred to milestone f (Orchestrator `single_job` mode).
- `orchestrator/` (LangGraph supervisor): `graph.py` = plans per mode (`recommend`, `outreach`, `single_job`), a pure `decide()` router, `_instrument()` (events + tracing + per-step failure policy), `build_graph/run_graph`. Every worker step returns to the `orchestrator` node, the single place that enforces: `run_max_steps` (LangGraph recursion limit is a backstop), budget (checked between steps; when exhausted it saves partial results instead of failing), and the Writer<->Critic rewrite cap (`critic_max_retries`). Failure policy: research failure = skip; writer/critic failure = keep best draft; anything else aborts with a safe message (no internals leaked). Planning is rule-based on purpose (fixed pipelines; an LLM planner adds cost, not value). `nodes.py` = step implementations on `Deps`; `state.py` = `RunState`/`Deps`; `events.py` = `EventSink` (replay + live fan-out, heartbeat); `manager.py` = `RunManager` (background asyncio task per run, ONE active run per user -> 409, run id == trace id, emit+persist+close with no await between so `run_finished` implies the DB row is final). LangGraph note: node ids are prefixed `step_` because a node cannot share a name with a state key.
- `recommend.py` / `outreach.generate_outreach` are thin wrappers that run the same graph to completion (sync endpoints `/recommendations/refresh`, `/outreach` still exist); they pass `persist=False` where the caller persists.
- Runs API (`api/routers/runs.py`): `POST /runs` (202; `recommend` | `outreach` + job_id | `single_job` + url and/or text), `GET /runs/active` (is one of MY runs still going? lets the dashboard re-attach after a reload), `GET /runs/{id}/events` (SSE: replays history, then live; finished runs replay from `runs.events_json`). There are deliberately NO list/detail routes for users; the `runs` table is internal (budgets, restart cleanup, aggregate stats). `start_run` MUST stay `async def` (it creates a task); sync handlers run in worker threads, so cross-thread cancellation uses `call_soon_threadsafe`.
- Pasted jobs (`agents/ingest.py`): text and/or URL -> `Job(source="pasted")`. Text wins (never fetched); URL-only goes through `tools/fetch.fetch_page_text` (SSRF guard). LinkedIn/Indeed/Naukri are refused for fetching (paste text instead; the link may still be kept as the user-supplied Apply link). `Job.apply_url` is optional ONLY for pasted text-only jobs. Pasted matches are `pinned=1` so a refresh never deletes them; the `pin` step stores the job before drafting so a failed draft still leaves it on the dashboard.
- Memory (`memory.py`): feedback notes (`POST /outreach/{id}/feedback`) + the user's last approved drafts feed the Writer as STYLE ONLY ("do not reuse facts"); the Critic still checks claims against the current fact sheet, so leaked facts get flagged. Bounded, per-user, deleted with the account.
- DB: `COLUMN_MIGRATIONS` in `db/connection.py` adds columns that shipped after a table's first release (CREATE TABLE IF NOT EXISTS never alters). New tables: `runs` (history + events), `feedback`.
- `eval/` (milestone g): `run_eval.py` CLI, `outreach_eval.py` (paired baseline vs multi-agent), `tiering_eval.py`, `p10_eval.py`, `judge.py` (INDEPENDENT fact-check / pairwise / relevance judges, never used by the product), `metrics.py` (bootstrap CI, paired diffs, Wilson, confusion), `report.py` (tables from saved JSON only), `build_dataset.py`, `datasets/` (frozen postings, labeled companies, 5 synthetic profiles), `results/` (raw JSON). Rules: both systems get the same inputs/model; judges are blind and see only each system's own sources; the product Critic score is reported but flagged circular; intervals spanning zero are "inconclusive"; tiering labels are UNVERIFIED drafts; P@10 relevance must be rated by a human (LLM proxy is always labelled as such). pytest has `pythonpath = ["."]` so `eval` imports in tests.
- Tiering (changed in g): the LLM estimates headcount and code applies the configured thresholds (`tier_from_employee_count`); the old prompt ("... or a multinational") made it label mid-size companies MNC (found by the eval).
- `Budget.calls` counts model calls; `OutreachResult.reports` keeps every critic report (first draft -> final).
- `agents/baseline.py`: single-agent baseline (control for the eval).

## Saved jobs, roles, companies (milestone C)
- `roles/taxonomy.py` + `data/roles.json`: deterministic role synonyms (SDE = Software Engineer = Software Development Engineer, FDE = Forward Deployed Engineer ...). `canonicalize`, `role_matches` (shared canonical role, one-way `RELATED` such as backend satisfies software engineer, substring, or all words of a custom role). Used by `sources/registry.matches` (discovery filter) and `agents/matcher.prefilter` (ranking); alerts (milestone D) build on it. `GET /roles/taxonomy`, `POST /roles/resolve`. Wanted roles are still `Profile.preferences.roles` (no separate table).
- `db/saved_repo.py` + `api/routers/saved.py`: `saved_jobs` (snapshot of the posting built ONLY from our stored job record, status, notes; `notes` and `snapshot_json` encrypted; `UNIQUE(user_id, job_id)`; saving requires the job to be in the user's matches; survives the job leaving matches/jobs) and `user_companies`. `listed` is maintained by `saved_repo.update_listing` after each discovery (`DiscoveryResult.seen_ids/sources_checked`): a job is declared gone only when its source answered with NO errors and the id is absent; pasted jobs are never touched. Migration 3 creates both tables; both are in export and cascade on account deletion.

## Alerts (milestone D)
- Idea: tell a user when a company they WATCH posts a role that fits one of their wanted roles, even under a different title. Package `alerts/`: `embedder.py` (default `HashingEmbedder`, dependency-free; optional `fastembed` via `ALERT_EMBEDDER=fastembed` falls back if missing; neither is a project dependency, and the scheduler is a small asyncio loop, not APScheduler, to avoid new dependencies), `matching.py` (`RoleScorer`: taxonomy match = certain; embedding similarity >= `alert_auto_threshold` = accepted with a template reason; between `alert_verify_threshold` and that = ONE batched LLM verification per user, accepted only with `match` and confidence >= `alert_min_confidence`; the LLM sees wanted roles and postings inside untrusted-data blocks, has no tools, and its one-line reason is link-stripped), `runner.py` (`run_alerts`: users with watched companies + roles + alerts on; fetch each needed board once via `sources.registry.fetch_boards`; skip jobs already alerted or judged; per-user daily cap; email digests; aggregate `alert_runs` row, no user ids), `store.py`, `mailer.py` (SMTP via `SMTP_*`; none configured = in-app only), `scheduler.py` (`ALERTS_ENABLED`, interval, no overlap).
- Guarantees that tests pin: `UNIQUE(user_id, job_id)` means never the same job twice (dismissing remembers the job in `alert_checked`); rejected jobs are remembered so the LLM is not asked again, unjudged ones (model failure/budget) are retried; at most `alert_daily_cap` per 24 h (leftovers are not marked judged); email is opt-in, goes ONLY to the account address, honours frequency (instant/daily/weekly/off), carries a visible link AND `List-Unsubscribe` one-click headers; the token is an HMAC with a per-user secret, `POST /alerts/unsubscribe` is public and CSRF-exempt, the frontend page `/unsubscribe` acts only on button press (GET never mutates). `why`, role and snapshot are encrypted. Migration 4. `update_listing` is NOT called from the alert pass (it fetches only a subset of boards).
- API `api/routers/alerts.py`: `/alerts`, `/alerts/summary`, `/alerts/settings` (GET/PUT, 409 if email requested but no mailer), `/alerts/read-all`, `/alerts/check` (caller only, 3/hour), `/alerts/{id}/read`, `DELETE /alerts/{id}`. Frontend: bell with unread count in `AppNav` (`components/shell/alerts-bell.tsx`), `/alerts` page, public `/unsubscribe`.

## Interview experiences + moderation (milestone E)
- Members only (every `/interviews*` route needs a session). Submit a STRUCTURED post (company, role, level, month, 1-10 rounds with a type, difficulty and notes about the KIND of questions, overall difficulty, outcome, tips, `anonymous` defaulting to true). `interviews/schemas.py` validators reduce every text field to plain text (tags, entities, control and invisible characters) and cap lengths; the frontend renders text only (no HTML anywhere).
- Pipeline (`interviews/moderation.py`, `api/routers/interviews.py::_screen`): rules first. Personal data (email, phone, link, secret-like token) is REJECTED with a 422 and never stored or sent to a model; attack language, a named individual, NDA/confidential wording, a dump of many exact questions, and AI-directed instructions are FLAGGED. Then an LLM classifier (untrusted-data block, no tools, schema output, reasons link-stripped); if it fails the post waits for a human (fail closed). The result (`auto_check_json`: flags, llm verdict, risk low/medium/high) only orders the admin queue; NOTHING is public until an admin approves (`status` pending -> approved), enforced inside `db/interview_repo` (public queries only ever return `approved`). Editing a post sends it back to pending and re-screens it; 5 submissions/edits per day, 10 pending per user; reports (one per user per post, not your own) from 3 distinct reporters hide a published post for re-review.
- Privacy: public responses never contain user ids, moderation data or email; `author` is a first name only when the author turned anonymity off. Admins (`api/routers/admin.py`, router-level `require_admin`, 404 for non-admins) see `author_id` and the auto-check, but reports never show who reported. Search uses a `search_text` column (the words people wrote, not field names), `%`/`_` are literal; the role filter goes through the role taxonomy. Account deletion deletes the user's posts, votes, reports and their moderation log (cascade). Migration 5.
- Frontend: `/interviews` (browse + "My posts"), `/interviews/new` (also `?edit=ID`; the `ConfidentialityNotice` and an acknowledgement checkbox are required), `/admin/moderation` (queue, reports, published; shows "Not found" when the server answers 404). The Moderation link in the account menu is only shown for `role === "admin"`, which is cosmetic: the server is the protection. Mock mode: the member is user 1, set `{"admin": true}` in `nextrole_mock` to preview the admin page.

## Security architecture (milestone B; see `docs/SECURITY.md`)
- **Field encryption** (`security/crypto.py`, `security/protect.py`): AES-256-GCM, keyring from `ENCRYPTION_KEYS` (first = active), ciphertext bound to `table.column:user_id`. `db/repos.py` seals/opens profile JSON, outreach draft/facts/critic/recipient and feedback notes; add a new PII column there AND to `ENCRYPTED_COLUMNS`. No plaintext fallback: without a key, saving personal data raises `CryptoNotConfigured`. The keyring is process-wide (`crypto.configure`, set in `create_app`); `tests/conftest.py` sets a test key. `RESUME_ENCRYPTION_KEY` (legacy Fernet) still works (a key is derived from it) and is upgraded at startup by `db/migrate.run_data_migrations`.
- **Migrations** (`db/migrate.py`): numbered, append-only, idempotent, a backup of an existing DB file goes to `<db dir>/backups/` before any pending one. Never edit a released migration; `schema.sql` is only the baseline. Never touch `data/nextrole.db` by hand.
- **Request security** (`security/web.py`, pure-ASGI middleware): headers on every response, Origin check on every write, double-submit CSRF token (`nextrole_csrf` cookie + `X-CSRF-Token`, sent by `lib/api/client.ts`) once logged in (logout and `/alerts/unsubscribe` are token-exempt). Tests build apps with explicit Settings to exercise it; `tests/conftest.py` turns CSRF and rate limits off by default through env.
- **Rate limits** (`security/ratelimit.py`, in memory; `api/deps.py`: `rate_limit_ip`, `rate_limit_user`): attach to every route that is expensive (LLM, upload, export) or abusable. `client_ip` trusts `X-Forwarded-For` only for `TRUSTED_PROXY_HOPS` proxies.
- **RBAC**: `users.role`; `require_admin` (404 for non-admins, role re-read from the DB every request); admins come only from `ADMIN_EMAILS`.
- **Untrusted text** (`llm/untrusted.py`): EVERY prompt that includes resume, posting, fetched page, user-written text or text derived from them wraps it with `wrap(label, text)` and the system prompt goes through `with_data_rule()`. Agents reading such text get no tools. Model output that reaches users is link-stripped by schema (`models/match.py`) or checked by `agents/output_guard.py` (the Critic's `rule_violations` includes it; a draft with a secret or prompt leak is withheld in `orchestrator/nodes.save`). `security/injection.py` is a tripwire, not the defence.
- **SSRF** (`tools/netguard.py`, `tools/fetch.py`): `resolve_public` + connection pinning; use `fetch_page_text` for ANY outbound fetch of a user- or page-supplied URL.
- **Privacy**: `GET /me/export` (sections registered with `@export_section` in `export.py`: add one for every new user-data table), `DELETE /me` (cascade + resume file + orphan pasted jobs + traces). `tests/security/test_privacy.py` asserts no table keeps a row for a deleted user: new tables need `user_id ... ON DELETE CASCADE`.

## Conventions
- Type hints everywhere; small functions; docstrings explain *why*.
- The LLM never generates or edits URLs. Agent outputs reference `job_id` only.
- Drafts are never auto-sent; human approval gates "ready to send".
- Ask before adding dependencies or making major architectural changes.
- Never commit secrets; `.env` is gitignored (`tests/security/test_repo_secrets.py` scans tracked files).
- New routes: take the user from the session (never the body), validate input with Pydantic, add rate limits to anything costly, return 404 not 403 for other users' objects, and add the data to export/delete.
